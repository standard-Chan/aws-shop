# Payment 설계가 과한 엔지니어링인지 점검

## 문제의식
- 앞서 정리한 해결 방향은 일관성 문제를 꽤 강하게 다루는 방식이다.
- 하지만 현재 서비스 규모와 요구사항에 비해 너무 복잡한 설계일 수 있다는 의문은 타당하다.
- 이 문서는 "정말 여기까지 해야 하는가?"를 점검하기 위한 문서다.

## 먼저 확인할 질문
- 사용자는 결제 생성 순간에 반드시 강한 일관성을 기대하는가
- 같은 `orderId`로 매우 짧은 시간 안에 중복 요청이 실제로 자주 들어오는가
- Payment 조회 실패가 치명적 장애인가, 아니면 잠시 후 재시도로 충분한가
- 운영 복잡도보다 데이터 정합성이 훨씬 더 중요한가

이 질문들에 대한 답이 모두 "예"가 아니라면, 현재 논의한 구조는 과할 수 있다.

## 지금까지 논의한 방식이 복잡한 이유
- `Order`와 `Payment`가 분리된 저장소/트랜잭션 경계를 가진다.
- 그런데 요구사항은 둘이 거의 원자적으로 움직이길 기대한다.
- 이 간극을 메우려다 보니 아래 요소들이 계속 추가된다.
  - 중간 상태
  - attempt 개념
  - `currentPaymentAttemptId`
  - 보상 처리
  - 정리 배치
  - 재시도/복구 규칙

즉, 복잡성의 원인은 "분산된 상태를 강하게 일치시키려는 것"이다.

## 더 쉬운 방법이 있을까

### 1. 가장 쉬운 방법: 조회 실패를 정상적인 일시 상태로 인정
핵심 아이디어:
- `Order=EXECUTING` 인데 Payment 가 아직 없을 수 있음을 시스템 계약으로 인정한다.
- 이 경우 즉시 실패 대신 `202 Accepted` 또는 비즈니스 예외 코드로 "결제 생성 중"을 반환한다.
- 클라이언트는 100ms~500ms 후 재조회한다.

#### 장점
- 구현이 가장 단순하다.
- 상태 머신을 거의 늘리지 않아도 된다.
- 기존 구조를 크게 바꾸지 않아도 된다.

#### 단점
- 강한 일관성은 포기한다.
- 클라이언트 재시도 정책이 필요하다.
- UX가 약간 투박해질 수 있다.

#### 언제 적합한가
- Payment 생성이 매우 짧게 끝나는 경우
- 사용자에게 "잠시만 기다려 주세요"가 허용되는 경우
- 내부 관리자 시스템이나 MVP 단계

## 2. 쉬운 방법: Payment 조회 실패 시 짧은 서버 내부 재시도
핵심 아이디어:
- 서버가 `EXECUTING + payment 없음` 상황을 만나면 즉시 실패하지 않는다.
- 50ms, 100ms, 200ms 정도 짧게 2~3회 재조회한다.
- 그 사이 생성되면 기존 Payment를 반환한다.

#### 장점
- 클라이언트 변경 없이 서버 안에서 흡수할 수 있다.
- 현재 구조를 거의 유지할 수 있다.

#### 단점
- 근본 해결은 아니다.
- 지연이 늘고, 고트래픽에서는 비효율적일 수 있다.
- 장애 상황과 단순 지연 상황을 깔끔하게 구분하기 어렵다.

#### 언제 적합한가
- 공백 구간이 매우 짧고 대부분 수 밀리초~수십 밀리초 안에 해소되는 경우
- 일단 운영 문제를 빠르게 줄이고 싶은 경우

## 3. 중간 난이도: Payment를 먼저 만들되 attempt 연결까지는 하지 않음
핵심 아이디어:
- Payment row 부재 문제만 없애고, 복잡한 `currentPaymentAttemptId`까지는 가지 않는다.
- 과거 검토에서는 `orderId` 기준 활성 Payment 하나만 유지하고 후행 요청이 active Payment 한 건을 재사용하는 방식을 고려했다.
- 현재 정책은 결제 실패 이력 보존을 위해 후행 생성 요청에서 기존 활성 Payment를 `FAILED`로 바꾸고 새 Payment를 생성한다.

#### 장점
- row 부재 문제는 줄일 수 있다.
- 설계 복잡도는 attempt 연결 방식보다 낮다.

#### 단점
- 경합이 심하면 "어느 Payment가 정답인가"가 다시 애매해질 수 있다.
- 보상 처리 중간에 애매한 상태가 남으면 복구 로직이 필요하다.

#### 평가
- 트래픽이 크지 않다면 현실적인 절충안이 될 수 있다.
- 다만 설계를 단순화한 만큼 모서리 케이스는 남는다.

## 4. 가장 현실적인 단순안
현재 요구사항 기준으로는 다음 조합이 가장 실용적일 가능성이 높다.

### 제안
- 기존 순서를 유지한다.
  - `Order -> EXECUTING 성공`
  - `Payment 생성`
- 대신 `EXECUTING인데 Payment 없음`을 즉시 장애로 보지 않는다.
- 서버 내부에서 짧게 재조회한다.
- 그래도 없으면 `결제 생성 중` 또는 `재시도 필요` 응답을 준다.
- 복구가 꼭 필요한 상황에서만 `pending` 복구를 시도한다.

### 왜 이게 단순한가
- 새로운 상태를 많이 추가하지 않는다.
- `attemptId` 같은 연결 모델도 추가하지 않는다.
- 클라이언트 또는 서버 재시도로 공백을 흡수한다.

### 왜 이게 충분할 수 있는가
- 실제 공백이 매우 짧다면 대부분 이 방식으로 해결된다.
- 모든 드문 타이밍 문제를 도메인 모델로 흡수하려 하면 비용이 너무 커진다.

## 언제 복잡한 설계가 정당화되는가
아래 조건이 많을수록 `attemptId + 중간 상태 + 보상 처리`가 정당화된다.

- 결제 생성 실패가 매출 손실로 직결된다.
- 동일 주문에 대한 동시 요청이 빈번하다.
- 클라이언트 재시도에 의존할 수 없다.
- 감사 추적과 복구 가능성이 매우 중요하다.
- 향후 환불/취소/재시도까지 결제 생명주기를 정교하게 관리해야 한다.

반대로 아래 조건이면 단순안이 더 낫다.

- 공백이 드물다.
- 짧은 재시도가 허용된다.
- 서비스가 아직 초기 단계다.
- 운영 복잡도를 낮추는 편이 더 중요하다.

## 추천 판단

### 지금 바로 적용할 1차 선택
- `EXECUTING + payment 없음`을 즉시 장애로 보지 않기
- 서버 내부 짧은 재조회 추가
- 그래도 없으면 `재시도 가능` 응답으로 전환

### 나중에 확장할 2차 선택
- 실제 운영에서 이 문제가 계속 발생하고
- 재시도로도 부족하다는 근거가 쌓이면
- 그때 `paymentAttemptId` 연결 모델로 간다

## 결론
- 네가 과한 엔지니어링을 걱정하는 건 맞는 방향이다.
- 현재 문제 하나만 놓고 보면, 가장 단순한 해법은 "공백을 오류가 아니라 일시 상태로 인정하고 재시도하는 것"이다.
- `attemptId` 기반 설계는 더 강한 정합성을 주지만, 그만큼 운영과 코드 복잡도도 크게 늘어난다.
- 따라서 지금 단계에서는 먼저 단순안으로 운영 데이터를 모으고, 실제로 부족할 때만 복잡한 설계로 가는 것이 더 실용적이다.
